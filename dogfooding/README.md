# _dogfooding — AttacheCase 5 の自己検証環境

リリース前に「一連の流れ」で確認するための場所。**git 追跡外**(`.gitignore` の `_*` に該当)。

```
_dogfooding\
├── run-all.ps1              ← 入口。層 1 → 層 1.5 → 層 2 の順に回す
├── RegressionTest\
│   └── run-tests.ps1        ← 層 1: 回帰スイート（仕様どおりか）
└── Tester\
    ├── Tester.csproj        ← 層 2: 総当たり（壊れないか）
    └── Program.cs
```

## 使い方

```powershell
# 事前に AttacheCase5.Private.sln を Release でビルドしておくこと

.\run-all.ps1                # 既定（層1 + 層2 を 50MB × 5 回）
.\run-all.ps1 -Quick         # 日常の確認（8MB × 3 回）
.\run-all.ps1 -Full          # リリース前（500MB × 20 回）
.\run-all.ps1 -SkipSoak      # 層 1 だけ
```

層 1 が落ちたら層 2 は実行しません。仕様が壊れている状態で負荷試験を回しても意味がないので。

終了コードは `0` = 全部通った、`1` = 失敗あり、`2` = 前提不備(未ビルドなど)。

## 層 1: 回帰スイート — 「仕様どおりか」

`RegressionTest\run-tests.ps1`。**数十秒**で終わります。コードを変えるたびに回す前提。

```powershell
.\RegressionTest\run-tests.ps1
.\RegressionTest\run-tests.ps1 -Filter "旧形式*"   # 絞り込み
.\RegressionTest\run-tests.ps1 -KeepWork           # 作業フォルダーを残す（調査用）
```

### なぜ今これが書けるのか

**`AttacheCase.Cli.exe` が終了コードを返すようになったからです。**

従来は GUI を起動して「ファイルが増えたか」で推測するしかなく、「誤ったパスワードなら 4 を返すこと」のような**異常系のアサーション**が書けませんでした。いまは書けます。回帰スイートの価値の半分はここにあります。

### 検証項目(45 件)

| 群 | 内容 |
|---|---|
| **A. 基本ラウンドトリップ** | 単一ファイル / フォルダー / 自己実行形式 / `/oneby` / `/autoname`(書式・連番) / `/camoext` / `/withext` / 処理種別の自動判定 |
| **B. 旧形式の復号互換** | v105(AC2) / v130(AC3) / v140(AC4)。**旧バージョンの本体で検体を毎回生成**して復号し、ハッシュを照合する |
| **C. 公開鍵方式** | 公開鍵で暗号化 → 秘密鍵で復号 / 別人の鍵では失敗 / パスワードで開こうとしたときの案内 |
| **D. 異常系と終了コード** | 誤パスワード=4 / 上書き禁止=5 / 不明オプション=2 / 入力なし=3 / **改ざん検出=8**(Argon2 パラメータ 3 種・鍵サイズ・切り詰め) / 非対応形式=9 |
| **E. 元ファイルの削除** | `/del=1` / `/del=3` / `/del=2`(**ごみ箱に入ったことを Shell COM で確認**) / UNC 拒否時に元ファイルが残ること / `/delenc` |
| **F. パスワードファイルほか** | パスワードファイルのラウンドトリップ / 1 バイト違うと開けないこと / `/list` / `--help` / **結果パスが標準出力へ出ること** |
| **G. 本体 GUI の経路** | GUI をコマンドラインで駆動して暗号化 / **GUI ⇄ CLI の相互復号** / 廃止オプションでエラーにならないこと |
| **H. Post-PPAP** | キーサーバから公開鍵を引いて暗号化 / 自己ラウンドトリップ / 未登録アドレスの扱い / アカウント未登録時の断り方。**既定では実行しない**(下記) |

### H 群(Post-PPAP)を既定で実行しない理由

`-PostPpap` を付けたときだけ走ります(`run-all.ps1 -Full` では自動的に有効)。

**本番のキーサーバへ問い合わせるから**です。検索 API はサーバ側で `lastSeen` を自動更新し、
列挙攻撃対策で 1 秒の意図的な遅延が入ります。日常の確認ループで毎回叩くものではありません。

```powershell
.\RegressionTest\run-tests.ps1 -PostPpap
.\RegressionTest\run-tests.ps1 -PostPpap -PostPpapEmail "someone@example.com"
```

#### 自己ラウンドトリップ(H-02)には「この PC での登録」が必要です

**秘密鍵はサーバから取得できません。設計上、キーサーバが持っているのは公開鍵だけです。**

| | 鍵の出どころ | ネットワーク | この PC での登録 |
|---|---|---|---|
| `/p-ppap=EMAIL`(暗号化) | サーバ上の**公開鍵** | 必要 | **不要** |
| `/p-ppap`(復号) | この PC の `accounts.json` の**秘密鍵**(DPAPI 保護) | 不要 | **必要** |

秘密鍵は `%APPDATA%\AttacheCase\PostPPAP\accounts.json` に、DPAPI で
「この PC・このユーザー」に紐付けて保存されます。したがって

- **メールアドレスを知っているだけでは自己復号テストはできません**
- 別の PC で登録していても、この PC では使えません
  (`_TODO.md` の「秘密鍵のバックアップ・PC 移行機能」が未実装なのと同じ理由)

登録が無い環境では H-02 は `SKIP` になり、代わりに H-04 が
「未登録なら復号を明示的に断ること」を確認します。

### 意図的に厳しくしている点

- **改ざん検出は所要時間も見ている。** 範囲検証が効いていれば Argon2 を呼ぶ前に落ちるので、5 秒以上かかったら失敗扱いにしています。「エラーにはなったが、その前に 2 TB 確保しようとしていた」を見逃さないため
- **B 群は検体を毎回生成し直します。** 固定の検体をコミットしておく方式だと、生成側の変化に気づけないので
- **G 群で GUI の実経路を通します。** `AttacheCase.exe /en=1 ... /exit=1` は本物の `Form1` を通るので、CLI だけでは触らないコードを踏めます

### 旧バージョンの本体の場所

B 群は次を参照します。無ければその項目は `SKIP` になります(失敗にはしません)。

| 形式 | 参照先 |
|---|---|
| v105 | `<ATC_LEGACY_ROOT>\AttacheCase5\_tools\Tester\AttacheCase.exe`(2.8.2.8) |
| v130 | `<ATC_LEGACY_ROOT>\AttacheCase3\AttacheCase\bin\Release\AttacheCase.exe` |
| v140 | `<ATC_LEGACY_ROOT>\AttacheCase4\AttacheCase\bin\Release\AttacheCase.exe` |

`<ATC_LEGACY_ROOT>` は環境変数 `ATC_LEGACY_ROOT`（既定 `D:\Dropbox`）です。別の PC で回すときはこの環境変数か `run-tests.ps1` の `$legacyExe` で調整してください。

### 旧形式の検体はキャッシュされます

検体は `%TEMP%\atc_regress_fixtures\` に置いて使い回します。旧本体を起動するのは初回だけです。
作り直したいときは `-RefreshFixtures` を付けてください(旧本体を入れ替えたときくらいです)。

**なぜキャッシュするのか。** 旧本体はコマンドラインで動かしても確認画面で止まることがあります
(AC5 では「`/p=` 指定時に確認画面で止まる」を 2026-04-13 に修正済みですが、**AC3 / AC4 には入っていません**)。
旧 Tester が `/mempexe=1` を付けていたのはこの回避のためで、本スイートも同じ組み合わせを渡しています。
それでも初回起動時のダイアログ等で止まる可能性は残るため、

- 検体はキャッシュして 2 回目以降は旧本体を起動しない
- 止まった場合は 30 秒でタイムアウトし、「確認画面で入力待ちになった可能性があります」と明示して**失敗**にする

という作りにしています。**人が横で押さないと通らないテストは、通っても意味がない**ので。

### 作業フォルダーは必ず Dropbox の外

層 1 は `%TEMP%\atc_regress_*`、層 2 は `%TEMP%\atc_soak_*` に作ります。
リポジトリ内や本体 exe と同じフォルダーには一切書きません(旧 Tester はそこを汚していました)。
`-KeepWork` / `/keep` を付けたときだけ残ります。

> 旧本体(AC2 / AC3 / AC4)を起動するので、それらのレジストリ設定に触れる可能性はあります。
> ただしコマンドライン引数がある場合は設定を保存しない作りなので、実害は確認されていません。

## 層 1.5: 設定画面スモーク — 「設定画面が開くか」

`Form3Smoke\Form3Smoke.exe`。本体を **ProjectReference で参照し、`Form3` を直接開く**。

### なぜ要るか

`Form3.cs` は 2026-08〜09 のレビューで **30 件以上**の指摘が出ている。にもかかわらず
層 1 は CLI と暗号化エンジンしか触らないので、**設定画面のコードは一度も実行されない**。
「ビルドが通った」以上の保証が無かった。

### 何を見るか

| | 内容 |
|---|---|
| A | `Form3` を開閉しながら**全ツリーノードを選択**して、例外が出ないか |
| A | 開閉を繰り返して **GDI / User ハンドルが増え続けないか** |
| B | **壊れた設定値**（範囲外のインデックスなど）でも開けるか、パネルが出るか |

### GDI ハンドルの閾値について

**1 周あたり 1.0 個以上増えたら失敗**にしている。根拠は実測（2026-09-05）:

| | 1 周あたりの増加 |
|---|---|
| 修正後 | **0.0 個** |
| `DestroyIcon` を外した状態 | **3.0 個**（`Form3_Load` が HICON を 3 つ作る） |

最初 5.0 にしていたら**漏れを見逃した**。実際に一度見逃している。
`Icon.FromHandle(bitmap.GetHicon())` は HICON の所有権を取らないので、
`DestroyIcon` を忘れると必ずここに出る。

### 使い方

```powershell
.\Form3Smoke\bin\Release\Form3Smoke.exe             # 既定（10 周）
.\Form3Smoke\bin\Release\Form3Smoke.exe 30          # 周回数を指定
.\Form3Smoke\bin\Release\Form3Smoke.exe 12 -tamper  # 壊れた設定値の検査も行う
```

`run-all.ps1` からは層 1 の直後に自動で走る（`-Quick` は 12 周、`-Full` は 30 周、
どちらも `-tamper` あり）。

### 実装メモ

- `AppSettings` は `internal` なので**リフレクション経由**で触る。
  テストのために本体側の可視性を変えない（`InternalsVisibleTo` も足さない）
- `Form3` は `public` なのでそのまま `new` できる
- ハンドル計測の基準は **2 周目**で取る。1 周目は遅延初期化のぶん増えるため

## 更新確認まわり（`UpdateCheck\`）

`AttacheCase\Update\` の検査。層 1 は CLI と暗号化エンジンしか触らないため、
更新確認のコードはそちらでは一度も実行されない。

### `verify-update.ps1` — 自動検査

```powershell
.\UpdateCheck\verify-update.ps1
```

鍵をその場で作って署名するので、**秘密鍵も配信サーバーもネットワークも要らない**。
0.2 秒ほどで終わる。見ているもの:

| 群 | 内容 |
|---|---|
| A | Ed25519 の分離署名。正しいものだけ受理するか |
| B | 最低 OS バージョンの判定（Windows は 3〜4 桁になる） |
| C | User-Agent の書式と、個体を識別する値が混ざっていないこと |
| D | **バージョン比較の桁**。4 桁目で版数を進めているので、丸めると更新を検出できない |
| E | 起動時に確認するかの判定（設定 OFF / コマンドライン起動 / 24 時間の間隔） |
| F | 設定 `fCheckUpdate` の既定が ON か |
| G | 配布物の Authenticode 検証。**改ざんを「署名なし」と誤って言わないこと**も見る |
| H | インストーラ版 / ZIP 版の判定 |
| I | 更新のお知らせダイアログのレイアウト（はみ出し・重なり・文言の出し分け） |
| J | 作業ディレクトリの後始末（できたばかりのものを消さない／掴んでいる間は消せない）と、配布ページの誘導先 |
| K | バージョン情報画面の更新確認リンクの位置（画面外へ出ていないか） |
| L | タイムアウトと、呼び出し側の中止の区別 |
| M | 起動する実体をマニフェスト（大きさと SHA-256）へ縛っているか |

⚠ **BouncyCastle は明示的に `LoadFrom` している。** Costura の埋め込み解決は
アプリの実行時にしか働かず、reflection で読むだけでは効かないため。

### `e2e-update.ps1` — 通し検査（自動）

```powershell
.\UpdateCheck\e2e-update.ps1
```

`verify-update.ps1` が部品ごとの検査なのに対し、こちらは**経路をつないで動かす**。

```
appcast を取りに行く → Ed25519 署名を検証する → JSON を解釈する
  → 現在の版と比べる → 配布物を選ぶ → 落とす → 大きさと SHA-256 を検証する
  → 掴んだまま保持する → お知らせ画面を組む
```

配信サーバーは `HttpMessageHandler` の差し替えで作る。**実際には通信しない**ので、
証明書もサーバーも要らず、外にも出ない。`UpdateService` と `UpdateDownloader` は
どちらも `HttpClient` を受け取れるので、本番のコードをそのまま通せる。

異常系も通す: 署名の改変・本文の改変・別の鍵・鍵が空・http のマニフェスト・
署名ファイルなし・http への降格リダイレクト・版が下がる・動かない OS・ハッシュ違いの配布物。

⚠ **ここで確認できないもの**（下の「リリース前のチェックリスト」を参照）

- 本物の https サーバーと証明書
- **署名済みインストーラの Authenticode 検証**
  開発ビルドは署名が無いため `GetRunningAppSigner()` が空を返し、そこで止まる
- インストーラの起動（UAC）と、インストーラ版としての判定

### `show-update-dialog.ps1` — 見た目の確認（手動）

```powershell
.\UpdateCheck\show-update-dialog.ps1 installer   # インストーラ版のボタン構成
.\UpdateCheck\show-update-dialog.ps1 zip         # ZIP 版（誘導のみ）
```

本番と同じ形の変更点を入れてダイアログを出す。配色や余白を調整するときに使う。
**対話的なターミナルで実行すること**（非対話だと即座に閉じる）。

## 層 2: 総当たり — 「壊れないか」

`Tester\`。ランダムなフォルダー構造と大量データを生成し、暗号化 → 復号 → ハッシュ照合を指定回数繰り返します。

`_tools\Tester\` にあった 2016 年製のツールが元です。ver.5 向けに次を変えました。

- **`AttacheCase.Cli.exe` を既定で駆動し、終了コードで成否を判定**する(旧版は GUI 起動して推測するだけだった)
- **作業フォルダーを分離**した(旧版は本体 exe と同じフォルダーにダミーデータを撒いていた)
- **対話待ちを既定でしない**。自動実行できる
- **ツール自身が終了コードを返す**(0 = 全試行成功)。`run-all.ps1` から連鎖できる
- ハッシュを MD5 → **SHA-256**
- 廃止された `/devcl` を除去

```powershell
Tester.exe /en=<AttacheCase.Cli.exe のパス> /size=200MB /num=20

# 別バージョン間の相互運用（GUI 駆動）
Tester.exe /en=<v5 の本体> /de=<別ビルドの本体> /gui
```

主なオプション: `/en=` `/de=` `/work=` `/p=` `/size=` `/range` `/type=0|1` `/num=` `/gui` `/keep` `/pause`
(`Tester.exe` を引数なしで実行すると一覧が出ます)

### 層 1 と役割が違う点

層 2 は**仕様を確認しません**。ランダムな構造と大きなデータで「壊れないこと」だけを見ます。深い階層、巨大ファイル、多数のファイル、といった層 1 では踏まない領域を踏むのが目的です。

### 多重起動の引数転送（`MultiInstance\`）

```powershell
.\_dogfooding\MultiInstance\test-arg-forward.ps1
```

回帰スイートは常に単一インスタンスで走るので、Mutex の `isNew` 側しか通りません。
このスクリプトは 1 つ目を起動したうえで 2 つ目をファイル付きで起動し、
2 つ目が自分で終了すること・1 つ目にパスワード入力欄が現れること（＝引数が届いたこと）を見ます。

> **⚠ この経路は 2026-09-07 まで壊れていました。**
> 送信側（`Program.Main`）は `WM_COPYDATA` を送っていたのに、
> **受け取るコードがどこにも無く**、既定のウィンドウプロシージャが捨てていました。
> `SendMessageTimeout` は「送れたか」しか返さないため、2 つ目のプロセスは
> 転送できたつもりで終了し、利用者が指定したファイルは黙って消えていました（ver.4 から）。
> 受信側 `Form1.WndProc` と、送信側の戻り値判定を直してあります。

自動化できない追加確認:

- [ ] 1 つ目の画面に、渡したファイル名が出ているか
- [ ] 1 つ目がモーダルダイアログ（INI 承認など）を出している最中に 2 つ目を起動したとき、
      2 つ目が自分でウィンドウを出すこと（受け取れないので送信側にフォールバックする）
- [ ] 1 つ目が暗号化・復号の処理中のときに 2 つ目を起動しても、処理が壊れないこと

### パスワード付き ZIP 画面（自動化できない）

ZIP 画面のドラッグ＆ドロップは CLI から触れないので、回帰スイートの対象外です。
`AttacheCase.exe` を起動し、サイドバーの「暗号化ZIP」を開いて確認します。

**判定は落とされたファイルの中身で決まります（独自形式と同じ）。画面のどこへ落としたかは見ません。**

| 落としたもの | 動き |
|---|---|
| ZIP ファイル（暗号化の有無を問わず） | **展開する** |
| フォルダー、ふつうのファイル、混在 | **暗号化 ZIP を作る** |
| `.docx` などの「中身は ZIP だが書庫ではない」ファイル | **暗号化 ZIP を作る**（展開しない） |

- [ ] 暗号方式のラジオボタンが「Standard ZIP 2.0」で開くこと（初回起動時の既定）
- [ ] 「AES128」を選んで**アプリを終了 → 再起動**し、選択が残っていること（レジストリ往復）
- [ ] フォルダーを落とす → パスワードを入れて暗号化 ZIP ができること
      - [ ] Standard ZIP 2.0 で作ったものがエクスプローラーで開けること
      - [ ] AES128 で作ったものは 7-Zip 等で開けること（エクスプローラーは非対応）
- [ ] 「なし」を選んでフォルダーを落とす → **パスワードを訊かれずに**ふつうの ZIP ができること
- [ ] 暗号化 ZIP を落とす → パスワードを訊かれ、展開できること
- [ ] ふつうの ZIP を落とす → **パスワードを訊かれずに**展開できること
- [ ] 🚨 **`.docx` を落とす** → 展開されず、暗号化 ZIP が作られること

- [ ] ZIP とテキストを一緒に落とす → まとめて 1 つの暗号化 ZIP になること
- [ ] ZIP 画面から Esc でスタートページへ戻れること

      （ZIP が「前回と同じ種類」として記憶されていないこと）

### 更新確認（実物が要るので自動化できない）

**アップロードの順序**: 配布物（`atcsXXXX.exe` / `atcsXXXX.zip`）を先に上げ、
`appcast.json` と `appcast.json.sig` は**最後にセットで**上げる。逆にすると、その隙に
更新を確認した人が 404 を踏む。片方だけ差し替えると署名検証に落ち、全利用者の
更新確認が失敗する（Mac 版 `RELEASE.md` と同じ運用）。

- [ ] **署名済みの実物で通す** — 署名前のビルドでは `GetRunningAppSigner()` が空を返し、
      ダウンロードへ進まない。EV 署名を済ませた `AttacheCase.exe` で確認すること
- [ ] **配信サーバーに appcast を置いて、本物の https で拾えるか**
      （`appcast.json` と `appcast.json.sig` の両方。片方だけだと失敗する）
- [ ] **インストーラ版として判定されるか** — インストールした状態で「更新の確認」を実行し、
      「今すぐ更新」（ダウンロードして起動）が出ること。ZIP 版では「ダウンロードページを開く」になる
- [ ] **UAC が出てインストーラが起動し、本体が終了するか**
- [ ] 更新後に版数が上がり、次の起動で「最新です」になるか
- [ ] サーバー側のログに User-Agent が残るか
      （書式は `AttacheCase/5.0.0.3 (Windows 10.0.26200.0; x64)`。`_doc\更新確認のUserAgent.md`）
- [ ] `%APPDATA%\AttacheCase\update_check.json` に確認日時が記録され、
      24 時間は再確認しないこと
- [ ] 設定の「起動時に更新の有無を確認する」を OFF にすると、起動時に確認しないこと
